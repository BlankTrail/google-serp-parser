# Проверка продолжительности Google-сессии

`sessionprobe` выполняет последовательные поиски через один новый порт BlankTrail
и один явно заданный SOCKS5. Он использует `google.Session` из парсера, но не
использует пул, который может переоткрыть порт или сменить выход после ошибки.
Настройки работающего парсера не изменяются. Созданный порт закрывается при
нормальном завершении, ошибке и Ctrl+C.

```powershell
go build -o data/sessionprobe.exe ./scripts/sessionprobe
.\data\sessionprobe.exe `
  -settings gserp-settings.json `
  -upstream socks5://185.104.194.44:2334 `
  -gap 60s -count 22 -duration 45m `
  -output data/sessionprobe-60s.jsonl
```

Файл результата должен быть новым: существующий файл не перезаписывается.
Если прокси требует пароль, передавайте URL через `GSERP_PROBE_UPSTREAM`, чтобы
не оставлять пароль в аргументах процесса. API-ключ читается из settings и не
пишется в результат.

Для заведомо непроверенного выхода можно добавить `-max-errors 2`: проба
закроет порт после двух подряд неудачных поисков. `cold` остаётся истинным
до первого успешного получения выдачи; соединение, которое ни разу не
получило выдачу, не считается прогретой сессией.

## Что фиксирует прогон

- Версию и commit BlankTrail, номер порта, профиль и время открытия.
- Фактический промежуток от завершения поиска до начала следующего.
- Класс ответа, число результатов, время ответа, каждый клиентский HTTP-запрос
  (включая первый визит на главную и редиректы).
- Имена, домены, пути, `Expires` и `Max-Age` cookies из ответов. Значения cookies
  не записываются. Этот список показывает входящие изменения, но сам по себе
  не доказывает, что прокси применил каждое из них; сверять с исходящими именами
  в журнале и проверками пути обновления в BlankTrail.
- Снимки счётчиков солвера до и после поиска, отдельно по семействам защиты.
- Проверки внешнего IP перед серией, через каждые пять поисков и после серии.
- Число открытых портов, чтобы заметить постороннюю нагрузку на тот же сервис.

Пауза применяется между **поисками**. Первый поиск также посещает главную;
редиректы и внутренние действия Challenge Breaker дополнительных пауз не имеют.
Поэтому клиентские поиски, запросы на проводе, обнаруженные защиты и запуски
солвера — разные величины. Медленный ответ сам по себе не считается каптчей.

`keep_sessions` и Challenge Breaker включены. Политика неразрешённой каптчи —
`return_to_script`, повтор после ошибки апстрима выключен (`skip_retry`).
Другие внутренние пути восстановления солвера сохраняются и могут менять
профиль: их нужно проверять по журналу. HTTP keep-alive
выключен, как в штатной конфигурации парсера. Один поток не означает лимит в один
туннель: такой лимит блокировал бы дополнительные соединения самого солвера.

## Как интерпретировать

1. Первое получение выдачи — холодный запуск; его стоимость учитывается отдельно.
2. При наличии отладочного журнала BlankTrail сопоставить время и порт с событиями
   `solver: рядовая подстановка кук`, `solver: challenge detected` и завершениями
   солва. Достаточно имён и количества cookies; их значения сохранять не нужно.
3. Проверка гипотезы TTL требует серии дольше TTL, с запросами чаще TTL и без
   смены IP/профиля. Совпадающий номер порта сам по себе не доказывает сохранение
   внутренней сессии; API не раскрывает идентификатор пина и `LastOK`.
   `port_identity_stable` сравнивает только видимые метаданные; ротацию обратно
   в профиль с тем же именем можно обнаружить по журналу, а не по этому флагу.
4. Счётчики `/solver/stats` относятся ко всему сервису. `counters_isolated`
   проверяет открытые порты и эпоху счётчика в двух снимках, но не исключает
   краткую постороннюю активность между снимками. Журнал конкретного порта —
   более точное подтверждение. `seen` не следует считать полным счётчиком каптч
   solver-порта: сверять его с журналом и `families`.
5. Внешний IP проверяется выборочно. Совпадение этих проб не доказывает, что
   провайдер не менял выход между ними; выбор фиксированного прокси важен.
6. Если серия с паузой работает, это подтверждает конкретное сочетание выхода,
   профиля и паузы. Для сравнения пауз повторить серии последовательно с теми же
   условиями и несколькими новыми сессиями; одна серия не устанавливает
   универсальную безопасную частоту.

Увеличение паузы проверяет влияние частоты, но не гарантирует отсутствие каптчи:
оно не устраняет смену личности, непригодный выход или отказ Google принять
cookies после солва. Паузы длиннее TTL дополнительно проверяют простой сессии,
а не только снижение частоты.

Сводка и отбор событий по порту и времени (только разрешённые поля, без значений
cookies и URL с токенами):

```powershell
.\scripts\sessionprobe\summarize.ps1 `
  -InputPath data/sessionprobe-60s.jsonl `
  -ProxyLog 'C:\Users\akost\AppData\Local\Programs\BlankTrail Proxy\data\proxy.log' `
  -EventsOutput data/sessionprobe-60s-events.jsonl
```

`-ProxyLog` и `-EventsOutput` необязательны. Сводку можно читать во время работы;
`completed: false` означает, что серия ещё не завершена. Журнал должен покрывать
весь интервал прогона; ротация самого файла журнала может обрезать историю.

## Наблюдение существующего задания

`observe_job.py` читает API BlankTrail, состояние работающего парсера и его
SQLite без запуска поисковых запросов и без изменения задания или настроек.
Сетевое подключение к LAN API идёт напрямую, без системного HTTP-прокси.

```powershell
python scripts/sessionprobe/observe_job.py --job 10 --samples 13 --interval 30 --output data/job10-observation.jsonl
```

По умолчанию используются настройки и база из `C:/Sandbox`; можно указать
`--settings` и `--database`. UI парсера читается на `127.0.0.1:8080`.
Выборка портов: `20000 <= port < 21000` и `keep_sessions=true`; перед анализом
проверить соответствие этой выборки заданию. Поля `ui_counts` относятся к
текущему активному пулу, поэтому их нужно сопоставлять с `progress.running`.
Счётчики солвера относятся ко всему сервису.

Для журнала используется только `/bug-report/preview`: он возвращает последние
500 строк без отправки отчёта. В файл попадают разрешённые поля и категории
ошибок; upstream записывается хешем. При ошибках API возможны пробелы — они
отражаются в `errors`, отсутствие событий в пробеле ничего не доказывает.
Выходной файл создаётся исключительно новым, существующий не перезаписывается.
